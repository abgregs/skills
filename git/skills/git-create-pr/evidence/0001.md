```markdown
## Impact
- Fixes the bug where a refused start left the tap machine believing a recording was live, so the next tap was read as a stop and did nothing.
- Removes a second copy of the recording state, so the cancel path no longer needs a manual reset.
```

**Title:** `fix(hotkey): keep a refused tap from swallowing the next one`

```markdown
## Summary

In Single Tap and Double Tap modes, a start that `RiverSession` refused (model still preparing, permission missing, last dictation still transcribing) left `TapStateMachine` in `.recording`. The user's next tap read as a `stop` and did nothing, so starting took two taps. `TapStateMachine` now keeps only the double-tap timing and reads whether a recording is live from the session on every tap, so a refused start leaves nothing to undo.

## Changes

- `TapStateMachine`: remove the `.recording` state and `reset()`; `handleTap(isRecording:)` takes the session's state and returns `.stop` when it is recording.
- `HotkeyManager`: add the `isRecording` closure, pass it to `handleTap`, and remove `resetTapState()`.
- `RiverSession`: wire `hotkey.isRecording` to `currentState == .recording`, and drop the `resetTapState()` call in the cancel path, which the new design makes unnecessary.
- `TapStateMachineTests`, `HotkeyManagerTests`, `RiverSessionTests`: rewrite for the new signature and add coverage for refused starts.
- `docs/architecture/river-pipeline.md` and `CHANGELOG.md`: describe the new ownership of recording state and add a Fixed entry.

## Impact

`HotkeyManager.setActivationMode` now clears the tap machine's double-tap timing unconditionally. An active recording survives a live mode or key change because the next tap reads it from the session.

## Testing
```
