## Summary
In Single Tap and Double Tap modes, a tap the session turns down (model preparing, permission missing, previous dictation still transcribing) no longer swallows the user's next tap. The tap machine stops tracking "recording" itself and reads it from `RiverSession` on each tap.

## Scope
- `TapStateMachine`, `HotkeyManager`, `RiverSession`
- Tests: `TapStateMachineTests`, `HotkeyManagerTests`, `RiverSessionTests`
- `docs/architecture/river-pipeline.md`, `CHANGELOG.md`

- `TapStateMachine`: drop the `.recording` state and `reset()`; `handleTap(isRecording:)` takes the session's state and keeps only the double-tap timing.
- `HotkeyManager`: add an `isRecording` provider read on each completed tap; remove `resetTapState()`.
- `RiverSession`: wire `hotkey.isRecording` to `currentState == .recording`; drop the cancel-time tap reset, which is no longer needed.
- Update tests for the new contract and add session coverage; note the change in the architecture doc and CHANGELOG.

## Impact
- Fixes the bug where a refused start left the tap machine believing a recording was live, so the next tap was read as a stop and did nothing.
- Removes a second copy of the recording state, so the cancel path no longer needs a manual reset.
- Hold mode is unaffected.

**Title:** `fix(hotkey): keep a refused tap from swallowing the next one`

```markdown
## Summary

In Single Tap and Double Tap modes, a tap that `RiverSession` refused to act on (model still preparing, permission missing, last dictation still transcribing) swallowed the next tap. `TapStateMachine` had already moved to `.recording`, so the next tap read as a `stop` for a recording that never started. `TapStateMachine` now keeps only the double-tap timing, and each tap reads whether a recording is live from `RiverSession`.

## Changes

- `TapStateMachine`: remove the `.recording` state and `reset()`; `handleTap(isRecording:)` takes the session's recording state and returns `.stop` when it is true.
- `TapStateMachine.setMode`: clear a half-finished double tap on every mode change.
- `HotkeyManager`: add the `isRecording` closure and pass it to `handleTap`; remove `resetTapState()`.
- `RiverSession`: wire `hotkey.isRecording` to `currentState == .recording`; drop the `resetTapState()` call from the cancel path, which no longer needs it.
- `HotkeyManagerTests`, `RiverSessionTests`, `TapStateMachineTests`: rewrite for the new contract and cover a refused start followed by a tap.
- `CHANGELOG.md`, `docs/architecture/river-pipeline.md`: record the fix and the new source of the recording state.

## Impact

Hold mode does not route through the tap machine and keeps its behavior. A live mode or key change no longer needs special handling to keep a recording stoppable, because the session reports the recording.

## Testing

For the reviewer:
- [ ] `swift test` passes, including `TapStateMachineTests`, `HotkeyManagerTests` and `RiverSessionTests`
- [ ] In Single Tap mode, tap while "Preparing model" shows, then tap again once ready: the second tap starts a recording
- [ ] In Double Tap mode, start a recording, press the cancel gesture, then double-tap: a new recording starts without an extra tap
```
