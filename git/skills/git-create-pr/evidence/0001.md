**Title:** `fix(hotkey): keep a refused tap from swallowing the next one`

```markdown
## Summary
In Single Tap and Double Tap modes, a tap the session turns down (model preparing, permission missing, previous dictation still transcribing) no longer swallows the user's next tap. The tap machine stops tracking "recording" itself and reads it from `RiverSession` on each tap.

## Scope
- `TapStateMachine`, `HotkeyManager`, `RiverSession`
- Tests: `TapStateMachineTests`, `HotkeyManagerTests`, `RiverSessionTests`
- `docs/architecture/river-pipeline.md`, `CHANGELOG.md`

## Changes Made
- `TapStateMachine`: drop the `.recording` state and `reset()`; `handleTap(isRecording:)` takes the session's state and keeps only the double-tap timing.
- `HotkeyManager`: add an `isRecording` provider read on each completed tap; remove `resetTapState()`.
- `RiverSession`: wire `hotkey.isRecording` to `currentState == .recording`; drop the cancel-time tap reset, which is no longer needed.
- Update tests for the new contract and add session coverage; note the change in the architecture doc and CHANGELOG.

## Impact
- Fixes the bug where a refused start left the tap machine believing a recording was live, so the next tap was read as a stop and did nothing.
- Removes a second copy of the recording state, so the cancel path no longer needs a manual reset.
- Hold mode is unaffected.
```

**Title:** `fix(hotkey): read recording state from the session on each tap`

```markdown
## Summary

In Single Tap and Double Tap modes, a tap that `RiverSession` refused to start (model still preparing, permission missing, previous dictation still transcribing) left `TapStateMachine` in `.recording`, so the user's next tap read as a stop and did nothing. `TapStateMachine` now keeps only the double-tap timing, and `HotkeyManager` asks the session on each tap whether a recording is live.

## Changes

- `TapStateMachine`: drop the `.recording` state and the `reset()` method; `handleTap(isRecording:)` takes the session's state and returns `.stop` when it is true.
- `HotkeyManager`: add an `isRecording` closure, read on each completed tap in the tap modes; remove `resetTapState()`.
- `RiverSession`: wire `hotkey.isRecording` to `currentState == .recording`; remove the `resetTapState()` call from `handleCancel`, which the new design makes unnecessary.
- `HotkeyManagerTests`, `RiverSessionTests`, `TapStateMachineTests`: rewrite for the new `handleTap(isRecording:)` signature and add cases for a refused start.
- `CHANGELOG.md`: add a Fixed entry.
- `docs/architecture/river-pipeline.md`: describe where the recording state now lives.

## Impact

`setMode` now always clears the double-tap state; it no longer preserves `.recording`. A live mode change still stops an active recording on the next tap, because the session reports it.

## Testing

For the reviewer:
- [ ] Run `swift test` and confirm `TapStateMachineTests`, `HotkeyManagerTests`, and `RiverSessionTests` pass
- [ ] In Single Tap mode, tap while the model shows "Preparing model", then tap again once it is ready: the second tap starts a recording
- [ ] In Double Tap mode, start a recording, press the cancel gesture, then double tap: a new recording starts without an extra tap
```
