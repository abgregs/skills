**Title:** `fix(hotkey): keep a refused tap from swallowing the next one`

```markdown
## Summary

In Single Tap and Double Tap modes, a tap that `RiverSession` refuses (model still preparing, permission missing, previous dictation still transcribing) no longer makes the next tap do nothing. The tap machine now reads "is recording" from the session instead of tracking its own copy that could drift out of step.

## Changes

- `TapStateMachine`: drop the `.recording` state and `reset()`; `handleTap(isRecording:)` takes the session's state, and the machine keeps only double-tap timing. `setMode` now always clears to `.idle`.
- `HotkeyManager`: add an `isRecording` provider read on each completed tap; remove `resetTapState()`.
- `RiverSession`: wire `hotkey.isRecording` to `currentState == .recording`; drop the `resetTapState()` call in the cancel path, which is no longer needed.
- Tests: update `TapStateMachineTests` and `HotkeyManagerTests` for the new signature, and add `RiverSessionTests` coverage for refused starts and cancel.
- Docs: `CHANGELOG.md` entry under Fixed; `docs/architecture/river-pipeline.md` describes the new ownership.

## Impact

Hold mode is untouched. In tap modes, live-switching key or mode mid-recording still lets the next tap stop it, now because the session reports the recording rather than the machine remembering it.

## Testing

- [ ] `swift test` passes, including `TapStateMachineTests`, `HotkeyManagerTests`, and `RiverSessionTests`
- [ ] Single Tap mode: tap while the model is still preparing, then tap again once ready — the second tap starts recording
- [ ] Double Tap mode: a refused double tap followed by another double tap starts recording
- [ ] Start a recording and cancel it; the next tap starts a new recording rather than being consumed as a stop
- [ ] Switch activation mode during a recording; the next tap stops it
```
