# 0005 — a change inside one function, then an update

**Claim.** A change inside one function gets no diagram. On an update, the new body keeps what people added to the PR in GitHub: a ticked reviewer box, a closing keyword, and a screenshot.

**Input.** The same macOS app as 0001. One commit, four files, 56 insertions and 16 deletions: the focused-element read that runs before typing gets a 0.5 s Accessibility messaging timeout, so an app that does not answer can no longer block the main thread for several seconds, and a timed-out read still fails open. A constant, a test seam with one test, and one line of a pipeline doc come with it.

The case runs in two steps. Each arm first opens its PR. Then a script stands in for a reviewer on both PRs, editing each body as GitHub's web editor would: it ticks the first unticked box and appends `Closes #1` and a screenshot line. Both lines are made up for the fixture: issue #1 is unrelated and the attachment URL resolves to nothing. Each arm then runs again in its own clone, with no new commits.

|---|---|---|
| Open | `Open a pull request for this branch against base/84.` | `/eval:git-create-pr base/84` |
| Update | `Update the description of the open pull request for this branch.` | `/eval:git-create-pr base/84` |

Read the repo's `docs/conventions/git.md`, the commit message, and the full diff. Its first push was rejected while the six arms pushed to the fixture at once, so its first `gh pr create` failed; it pushed again and opened the PR. 7 turns, 28.5 s, $0.129.

**Title:** `fix(insert): bound the focused-element read with an AX timeout`

```markdown
## Summary
The insertion guard's focused-element read runs on the main thread, and an app that doesn't answer Accessibility could block it for the system default timeout on every call. This bounds the read at 0.5 s and fails open.

## Scope
- `Sources/River/Architecture/AccessibilityCapability.swift`
- `Sources/River/Utilities/Constants.swift`
- `Tests/RiverTests/CapabilityTests.swift`
- `docs/architecture/river-pipeline.md`

## Changes Made
- `readFocusedElementRole` sets `Constants.focusedElementReadTimeoutSeconds` (0.5 s) on the system-wide element, which is the process-wide AX default, so it also bounds the role and subrole reads.
- A timeout returns `kAXErrorCannotComplete` and classifies as `.unknown`, so typing proceeds.
- The unknown-role log line now includes the AX error code, so a timeout is visible in the field.
- Added the `focusedElementReadForTesting` seam, plus a test mapping `.cannotComplete` to `.unknown`.
- Comments in `AccessibilityCapability` now describe keystroke injection rather than the clipboard paste.
- `river-pipeline.md` notes the timeout.

## Impact
A hung target app costs at most 1.5 s (three AX calls) instead of several seconds per call. A healthy app answers in milliseconds. The guard fails open, so a too-short value loses only the guard, never the dictation. No settings or UI change.

## Testing
- [ ] `swift test` passes, including `readTimeoutFailsOpen`
- [ ] Dictate into an editable field with Accessibility granted (guard still works)
- [ ] Dictate while the focused app is unresponsive (typing proceeds after the timeout, log shows `axError=-25204`)

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

## Observations

- Neither arm drew a diagram. The change sits inside the focused-element read and the log line that reports it, a change inside one function, which is the case `SKILL.md` names for leaving one out.
- Both arms read the full diff. Bare's Changes bullet that the timeout "also bounds the role and subrole reads" is a fact the skill's body leaves out; the skill's Testing items say what result to look for in each check.
- On the update, the skill rewrote the body and kept all three of the reviewer's lines, each verbatim. It moved `Closes #1` into Summary, left the reviewer's tick under `For the reviewer:`, and put the screenshot after Testing. The lint, given `--existing`, would have failed a body missing any of them.
- Bare kept the three lines by not editing at all, and its reason holds: the branch had no new commits since the body was written. The skill rewrote anyway, because an update always writes a new body; the result says the same thing in two sentences where there had been one. This case shows the skill keeps added lines through a rewrite. It does not show a bare agent losing them, and bare's choice not to touch an up-to-date body is the better one here.
- Bare's body ends with the harness footer, and the reviewer's lines sit below it. The skill's has no footer.
- The skill cost $0.108 to open and $0.069 to update, against bare's $0.129 and $0.075. Bare's open includes a retried push and a failed `gh pr create`, both caused by the parallel pushes, not by bare.
