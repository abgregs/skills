# 0005 — a change inside one function, then a reviewed update

**Claim.** A change inside one function gets no diagram. When a new commit makes the body wrong after a reviewer has worked on it, the update rewrites the body for the new code and keeps what the reviewer added: a ticked box, a closing keyword, and a screenshot.

**Input.** The same macOS app as 0001. One commit, four files, 56 insertions and 16 deletions: the focused-element read that runs before typing gets a 0.5 s Accessibility messaging timeout, so an app that does not answer can no longer block the main thread for several seconds, and a timed-out read still fails open. A constant, a test seam with one test, and one line of a pipeline doc come with it.

The case runs in three steps. Each arm first opens its PR. Then two scripts stand in for people. A reviewer edits each body as GitHub's web editor would: it ticks the first unticked box and appends `Closes #1` and a screenshot line. An author pushes one follow-up commit to both branches with a plain `git push`, halving the timeout to 0.25 s and the worst case in its comment to 0.75 s, so each body's 0.5 s and 1.5 s figures go stale. The issue, the attachment URL, and the follow-up commit are all made up for the fixture. Each arm then runs again in its own clone.

### bare

**Title:** `fix(insert): bound the focused-element read with an AX timeout`

```markdown
## Summary
The insertion guard's focused-element read runs on the main thread, and an app that doesn't answer Accessibility could block it for the system default timeout on every call. This bounds the read at 0.5 s and fails open.

## Scope
- `Sources/River/Architecture/AccessibilityCapability.swift`
- `Sources/River/Utilities/Constants.swift`
- `Tests/RiverTests/CapabilityTests.swift`
- `docs/architecture/river-pipeline.md`

## Changes Made
- `readFocusedElementRole` sets `Constants.focusedElementReadTimeoutSeconds` (0.5 s) on the system-wide element, which is the process-wide AX default, so it also bounds the role and subrole reads.
- A timeout returns `kAXErrorCannotComplete` and classifies as `.unknown`, so typing proceeds.
- The unknown-role log line now includes the AX error code, so a timeout is visible in the field.
- Added the `focusedElementReadForTesting` seam, plus a test mapping `.cannotComplete` to `.unknown`.
- Comments in `AccessibilityCapability` now describe keystroke injection rather than the clipboard paste.
- `river-pipeline.md` notes the timeout.

## Impact
A hung target app costs at most 1.5 s (three AX calls) instead of several seconds per call. A healthy app answers in milliseconds. The guard fails open, so a too-short value loses only the guard, never the dictation. No settings or UI change.

- [ ] Dictate while the focused app is unresponsive (typing proceeds after the timeout, log shows `axError=-25204`)

🤖 Generated with [Claude Code](https://claude.com/claude-code)
```

**Title:** `fix(insert): bound the focused-element read with an AX timeout`

```markdown
## Summary

The focused-element read before typing ran on the main thread with the system default AX messaging timeout, so an app that did not answer blocked River for several seconds per call. `AccessibilityCapability` now sets a 0.5 s messaging timeout on that read, and a read that times out classifies as `.unknown`, so typing proceeds.

## Changes

- `AccessibilityCapability.readFocusedElementRole` calls `AXUIElementSetMessagingTimeout` on the system-wide element and returns the AX error beside the role and subrole
- `AccessibilityCapability.classifyFocusedTarget` logs the AX error code (`axError=`) when the role is unknown
- `AccessibilityCapability` gains the `focusedElementReadForTesting` seam, which replaces the real read in tests
- `Constants.focusedElementReadTimeoutSeconds` holds the 0.5 s value
- `FocusedTargetClassificationTests.readTimeoutFailsOpen` pins a `.cannotComplete` read to `.unknown`, with a control that an `AXButton` role still returns `.nonEditable`
- The `FocusedTargetClassification` doc comment and `docs/architecture/river-pipeline.md` describe keystroke insertion instead of paste, and the doc names the timeout

## Impact

- A hung app now costs at most 1.5 s (three AX calls at 0.5 s) instead of several seconds per call.
- On the system-wide element, the timeout is this process's global AX default, so it applies to every AX call River makes after the first focused-element read, not only this one.
- A read that times out loses the non-editable guard for that insertion. Dictation still types.

## Testing

For the reviewer:
- [ ] `swift test` passes, including `readTimeoutFailsOpen` in `Tests/RiverTests/CapabilityTests.swift`
- [ ] With a hung app focused (for example one paused in the debugger), dictate and confirm typing starts within about 1.5 s
- [ ] Confirm the 0.5 s value in `Constants.swift` leaves healthy apps unaffected, and that the global scope of the timeout is acceptable
```

## Observations

- Neither arm drew a diagram. The change sits inside the focused-element read and the log line that reports it, a change inside one function, which is the case `SKILL.md` names for leaving one out.
- The skill's open Summary leads with the problem: the read ran on the main thread with the system default timeout, so a hung app blocked River. Its Impact adds what bare's says only in a Changes bullet: on the system-wide element, the timeout becomes the process's default for every AX call.
- On the update, the follow-up commit reached the PR outside the skill, so the preflight found no push to make; the skill compared the body with the diff, found the figures stale, and rewrote. Every figure moved: 0.25 s in Summary, Changes, and Testing, 0.75 s in Impact and the manual check.
- The skill's new body kept all three of the reviewer's lines verbatim, the tick still under `For the reviewer:`; the gate would have refused a body that dropped one.
- Bare kept them too, by editing the three figures in place and leaving every other line alone. This case shows the skill keeps people's lines through a full rewrite. It does not show a bare agent losing them: given a write path, bare chose the smallest edit.
- Bare noticed what the skill did not: the reviewer's tick on `swift test` predates the follow-up commit, so nobody has run the tests against 0.25 s. The skill kept the tick verbatim, as the rule asks, without saying it is stale.
- Bare's body still ends with the harness footer, with the reviewer's lines below it. The skill's has no footer.
- Opening cost $0.110 for the skill against $0.129 for bare, whose number includes a retried push. The update cost $0.111 against $0.077.
