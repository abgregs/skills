# 0003 — a repo with its own subject format

**Claim.** The `type(scope): description` format is a default. When the repo enforces a format of its own, the skill writes subjects in the repo's shape, its lint skips the format check, and the repo's hook stays the judge.

**Input.** A fixture repo built for this case. Four commits of history, all ticket style:

```
f67dfb1 WID-4: add the contributing rules
9037171 WID-3: format numbers with two decimals
9d49267 WID-2: document the call order
563f08d WID-1: add the parse and fmt helpers
```

`core.hooksPath` points at `hooks/`. Fed the conventional subject `fix(parse): handle null` before the run, the hook rejected it. Two files were dirty: `src/parse.js` gained a null guard, and `README.md` gained a section describing it. The files as the run found them:

`CONTRIBUTING.md`

```
# Contributing

Every commit subject starts with its ticket id: `WID-<n>: <summary>`.
The hook in `hooks/` rejects any other subject. The next free ticket is WID-5.
```

`hooks/commit-msg`

```sh
#!/bin/sh
head -1 "$1" | grep -qE '^WID-[0-9]+: ' && exit 0
echo 'commit-msg: subject must start with WID-<n>: ' >&2
exit 1
```

`src/parse.js` (the `if` line is the dirty change)

```js
function parse(input) {
  if (input == null) return "";
  return String(input).trim();
}

module.exports = { parse };
```

`src/fmt.js`

```js
function fmt(n) {
  return Number(n).toFixed(2);
}

module.exports = { fmt };
```

`README.md` (the `## Null input` section is the dirty change)

```
# widgets

Call `parse` on raw input, then `fmt` on the number you derive from it.

## Null input

`parse` returns an empty string for `null` or `undefined`.
```

## skill — 1 commit

```
commit 5618ef6      README.md, src/parse.js
WID-5: return empty string from parse for null input

- `parse` returns an empty string for `null` or `undefined`
- `README.md` documents the null input case
```

Tool calls, in order:

1. Preflight, which reported `subject format: REPO-ENFORCED (hooks/commit-msg)`.
2. `git diff` and `cat hooks/commit-msg`, reading the hook that enforces the rule.
3. `ls`, `git show --stat` of the last commit, and `cat CONTRIBUTING*`, reading the written rule and the next free ticket.
4. One call: `git add README.md src/parse.js` → `mktemp` → `printf` the message → `--commit`.

The lint printed `repo enforces its own subject format (hooks/commit-msg) — type(scope) checks skipped` and passed the message. The hook accepted it on the first try. 5 turns, 110.0 s (run alongside the 0005 probe), $0.067.

## Observations

- The subject follows the repo, not the skill: ticket id, next free number, no type or scope.
- The README section describes the null guard, so it went in the same commit under the same ticket.
- No `Why:`. A null guard has no cause from outside the code.
- Everything the lint still enforces held: subject under 72 characters, blank line, dash bullets, no trailer.
- The skill read the hook source and `CONTRIBUTING.md` before writing, so it followed the real rule rather than guessing from history alone.
- No bare arm was run. The question here is whether the skill defers, not how it compares.
