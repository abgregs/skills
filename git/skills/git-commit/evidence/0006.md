# 0006 — a branch of separate changes

**Claim.** When a tree holds changes that each stand alone, the skill splits them: by type, then by what calls the new code. Work of one type with one purpose across several files is a close call, and it stays one commit when one reviewer could read it in a sitting.

**Input.** The same macOS app as 0001. Ten files, 294 insertions and 13 deletions. Nine are modified; one, a CI workflow, is new and was marked with `git add -N` so it counts as a tracked change. The change set holds three kinds of work:

- a new GitHub Actions workflow that runs the test suite (`.github/workflows/ci.yml`, 67 lines);
- the empty-prompt retry rule extracted from `TranscriptionService.transcribe` into `resolveWithEmptyPromptRetry(promptTokens:decode:)`, which takes the decode step as a closure; `transcribe` calls it with the real decoder, and three new tests in `TranscriptionServiceTests.swift` call it with fakes. One line in `docs/conventions/tests.md` lists the new seam;
- tests that close coverage gaps in six other suites: 149 changed lines across `ActivationModeTests`, `AppStateTests`, `AudioCaptureManagerTests`, `SettingsStoreTests`, and `TapStateMachineTests`, plus one always-true assertion removed from `TextInsertionManagerTests`.

The repo's `docs/conventions/git.md` is as described in 0001.

## Observations

- The skill made three commits, each of which stands alone: the workflow, the seam with its tests and doc line, and the coverage-gap tests. Bare made two, putting the seam and all nine test and doc files in one `test` commit.
- The six coverage-gap files were the close call. The skill ran `--size`, got 149 lines, and kept them as one commit. An earlier run, on the skill before close calls were weighed by review, gave each of the six files a commit of its own, eight commits in all; that run is why one purpose across several targets is now weighed by review time rather than split by target.
- The skill kept the extraction with its tests and typed the group `test`. The rule for a new symbol that existing code already calls, here `transcribe`, says it lands first as its own commit with its own tests and docs. That gives the same three files in one commit but types it `refactor`. So the grouping follows the rule and the type does not; the skill's reading, that the extraction exists only for the tests, is the one the type rule for a test seam describes.
- The branch's own history has the same three commits, in the order `ci`, `test(transcription)`, `test`. That history is not an answer key (see the README's "What is compared"), but it shows the split is one a maintainer chose.
- The skill's summary admits it wrote one bullet from diff stats without reading two of the diffs. The bullet is accurate against the diff, but the run did less reading than its message implies.
- Bare appended the trailer to both commits; the skill did not.
- Bare committed the workflow by path and the rest with `git add -A`. The skill named each commit's paths to the gate and staged nothing by hand.
