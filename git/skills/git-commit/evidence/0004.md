# 0004 — a tangled branch

**Claim.** On a real branch whose parts share files, the skill separates changes by type and outcome, but when one source file holds pieces of two changes, it commits them together and says why, so no commit lands without code it needs. The joined commit leads with one `Why:` and gives the joined change a bullet of its own.

**Input.** The same macOS app as 0001. Fourteen files, 588 insertions and 28 deletions. Thirteen are modified; one, a planning doc, is new and was marked with `git add -N` so it counts as a tracked change. The change set is one branch that was first committed as six commits: a fix that keeps recording when the input device changes, a fix that bounds the audio a recording may lose, a feature that ends a recording early when its audio stops arriving, a follow-up fix to that feature, and two planning docs. Several intents share files: `AudioCaptureManager.swift`, `RiverSessionTests.swift`, and `CHANGELOG.md` each carry more than one. The repo's `docs/conventions/git.md` is as described in 0001.

## bare — 1 commit, all 14 files

```
commit d285300
fix(audio): survive a device change during the first recording

The first recording after launch with AirPods connected lost its audio:
CoreAudio rebuilt the default-device aggregate mid-recording, stopping
the engine, and River never observed AVAudioEngineConfigurationChange.

- MicrophoneCapability observes the configuration change, re-reads the
  input format, reinstalls the tap, and restarts the engine in place.
- AudioCaptureManager.convert splits the recording into same-format
  runs so a 24 kHz -> 48 kHz switch is resampled correctly.
- stopRecording throws captureIncomplete when captured audio falls more
  than 1 s short of wall time; a watchdog checks the same gap during
  the recording and ends it early, typing what was heard.
- A dedicated toast explains a cut-short recording.

Adds tests, planning record 0032, pipeline/test docs, and a changelog entry.

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

Tool calls: `git status/diff --stat/log/branch`, a Read of the new planning record, then `git checkout -b fix/device-switch && git add -A && git commit -F - <<EOF`, taking the branch name from the planning record. 4 turns, 159.1 s (run alongside the 0005 probe), $0.074.

## skill — 1 commit, all 14 files

```
commit 1d033a2
fix(audio): survive input device changes mid-recording

- Why: a first recording with AirPods ran 14 s on an engine stopped at 1.7 s and typed nothing
- `MicrophoneCapability` reinstalls the tap and restarts the engine on a configuration change
- `AudioCaptureManager.convert` resamples each run of same-format buffers with its own converter
- `AudioCaptureManager` throws `captureIncomplete` when audio trails the clock by over 1 s
- `RiverSession` types the text heard before a capture failure, then reports the error
- `ErrorToastPresentation` shows "Recording cut short" for `captureIncomplete`
```

Its summary to the user: "`AudioCaptureManager.swift` holds both changes. One is the engine restart with per-format conversion. The other is the capture-gap check with its watchdog. A commit takes whole files, so the two outcomes are bound together. The tests, docs, changelog and planning entry cover that same set of changes, so they went in too."

Tool calls: preflight, `git diff` of the changelog, sources, and docs with the status of the new planning file, `git diff` of the sources, then `--commit` with the fourteen paths after `--`, twice. The first message had two lines over 100 characters, so the gate stopped it with exit 2; the skill trimmed them in the same file, and the gate committed. 6 turns, 23.3 s, $0.173.

### Four more skill runs

The skill arm ran four more times on copies of the same tree, on the same skill, in parallel. Each made the same one commit of fourteen files.

## Observations

- Both arms made one commit of fourteen files, for different reasons. Bare treated the branch as one change. The skill found two fixes, the engine restart and the capture-gap check, and joined them because `AudioCaptureManager.swift` holds code for both: the conversion the restart needs and the gap check. All five skill runs joined them; on the skill before, one run of five read the conversion as part of the gap fix and split the two the other way the rules allow, each commit standing.
- The gap check has bullets of its own, the `captureIncomplete` throw, the text the session types, and the toast. Only the lead change has the `Why:`, as the rule for a joined change asks.
- The skill typed the whole change `fix`, reading a recording that silently loses audio as broken behavior. That fits the skill's definition of a fix, and `feat`, for ending a recording early, fits the watchdog too. The branch's own history called the watchdog a `feat`, but that history is not an answer key (see the README's "What is compared").
- The `Why:` carries the measured figure, an engine stopped 1.7 s into a 14 s recording, which the subject cannot. Bare's opening paragraph gives the same cause in prose, without the figure.
- Every skill body names the code that acts in each bullet and has six bullets, the most the skill allows; on the skill before, these runs wrote five. Every extra run's first draft went over the cap.
- Neither arm read the repo's `docs/conventions/git.md` in this run. The skill does not by design: it defers to a format the repo enforces, as in 0003, not to prose. One convention that costs is the doc's "wrap at ~72 columns"; every line of the skill's body runs past 72 characters, the longest to 96.
- Bare staged with `git add -A`; every skill run named its paths to the gate and staged nothing by hand.
