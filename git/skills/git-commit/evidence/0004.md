# 0004 — a tangled branch

**Claim.** On a real branch whose parts share files, the skill separates changes by type and outcome, but when one source file holds pieces of two changes, it commits them together and says why, so no commit lands without code it needs. The joined commit leads with one `Why:` and gives the joined change a bullet of its own.

**Input.** The same macOS app as 0001. Fourteen files, 588 insertions and 28 deletions. Thirteen are modified; one, a planning doc, is new and was marked with `git add -N` so it counts as a tracked change. The change set is one branch that was first committed as six commits: a fix that keeps recording when the input device changes, a fix that bounds the audio a recording may lose, a feature that ends a recording early when its audio stops arriving, a follow-up fix to that feature, and two planning docs. Several intents share files: `AudioCaptureManager.swift`, `RiverSessionTests.swift`, and `CHANGELOG.md` each carry more than one. The repo's `docs/conventions/git.md` is as described in 0001.

## bare — 1 commit, all 14 files

```
commit d285300
fix(audio): survive a device change during the first recording

The first recording after launch with AirPods connected lost its audio:
CoreAudio rebuilt the default-device aggregate mid-recording, stopping
the engine, and River never observed AVAudioEngineConfigurationChange.

- MicrophoneCapability observes the configuration change, re-reads the
  input format, reinstalls the tap, and restarts the engine in place.
- AudioCaptureManager.convert splits the recording into same-format
  runs so a 24 kHz -> 48 kHz switch is resampled correctly.
- stopRecording throws captureIncomplete when captured audio falls more
  than 1 s short of wall time; a watchdog checks the same gap during
  the recording and ends it early, typing what was heard.
- A dedicated toast explains a cut-short recording.

Adds tests, planning record 0032, pipeline/test docs, and a changelog entry.

Co-Authored-By: Claude Sonnet 5.5 <noreply@anthropic.com>
```

Tool calls: `git status/diff --stat/log/branch`, a Read of the new planning record, then `git checkout -b fix/device-switch && git add -A && git commit -F - <<EOF`, taking the branch name from the planning record. 4 turns, 159.1 s (run alongside the 0005 probe), $0.074.

## skill — 1 commit, all 14 files

```
commit 83b3035
fix(audio): restart the engine on a mid-recording device change

- Why: AirPods entered call mode on first mic open and the engine died 1.7 s into a 14 s recording
- `MicrophoneCapability` restarts the engine and tap on `AVAudioEngineConfigurationChange`
- `AudioCaptureManager.convert` resamples each run of same-format buffers on its own
- `stopRecording` throws `captureIncomplete` on a 1 s audio gap, so a failed restart is not typed
  as the whole; a watchdog ends the recording early and the session types the heard text
```

Its summary to the user: "I didn't split it because `AudioCaptureManager.swift` holds both the mixed-format conversion and the capture-gap check, and a commit takes whole files. Everything else is bound to one of those two changes." It then lists which files belong to the engine restart and which to the gap check, and says "The commit body gives the gap check its own bullet."

Tool calls: preflight, `git diff` of the sources and changelog, `git diff` of the docs with a read of the new planning record, then `--commit` with the fourteen paths after `--`, three times. The first message had four lines over 100 characters, the longest 124; the second had one, at 107; the skill wrapped that bullet onto an indented second line, and the third passed and committed. 7 turns, 260.2 s (run alongside the 0005 probe), $0.211.

## Observations

- Both arms made one commit of fourteen files, for different reasons. Bare treated the branch as one change. The skill found two fixes, the engine restart and the capture-gap check, and joined them because `AudioCaptureManager.swift` holds code for both; its summary says so and assigns every other file to one of the two.
- Two earlier runs shaped the rules this run follows. One split the two fixes by file and put the shared file in the later commit, so the first commit's engine restart landed before the conversion it relies on; that run is why a shared source file joins its changes. Another, on the skill before its grouping rules were audited, made a `fix` of ten files and a separate `docs` commit for the pipeline doc, the test conventions, and the planning record; that run, with the same split in 0002, is why a doc that describes exactly the other change binds to it.
- The joined change, the gap check, has a bullet of its own that says what it guards against: a failed restart typed as if it were the whole recording. Only the lead change has the `Why:`, as the rule for a joined change asks.
- The skill typed the whole change `fix`, reading a recording that silently loses audio as broken behavior. That fits the skill's definition of a fix, and `feat`, for ending a recording early, fits the watchdog too. The branch's own history called the watchdog a `feat`, but that history is not an answer key (see the README's "What is compared").
- The `Why:` carries the measured figure, a stop 1.7 s into a 14 s recording, which the subject cannot. Bare's opening paragraph gives the same cause in prose, without the figure.
- The gate stopped this commit twice. The skill trimmed or wrapped each flagged line rather than passing `--accept-warnings`, and the third message passed.
- Neither arm read the repo's `docs/conventions/git.md` in this run. The skill does not by design: it defers to a format the repo enforces, as in 0003, not to prose. One convention that costs is the doc's "wrap at ~72 columns"; every line of the skill's body runs past 72 characters, the longest to 98.
- Bare created a branch and staged with `git add -A`; the skill named all fourteen paths to the gate and staged nothing by hand.
