# 0004 — a tangled branch

**Claim.** On a real branch whose parts share files, the skill splits along the conventional type and then along "the same fix or a different one", and a file that serves two commits goes in the later one.

**Input.** The same macOS app as 0001. Fourteen files, 588 insertions and 28 deletions. Thirteen are modified; one, a planning doc, is new and was marked with `git add -N` so it counts as a tracked change. The change set is one branch that was first committed as six commits: a fix that keeps recording when the input device changes, a fix that bounds the audio a recording may lose, a feature that ends a recording early when its audio stops arriving, a follow-up fix to that feature, and two planning docs. Several intents share files: `AudioCaptureManager.swift`, `RiverSessionTests.swift`, and `CHANGELOG.md` each carry more than one. The repo's `docs/conventions/git.md` is as described in 0001.

## bare — 1 commit, all 14 files

```
commit b9139e7
fix(audio): survive a device change during the first recording

- `MicrophoneCapability` observes `.AVAudioEngineConfigurationChange`,
  re-reads the input format, reinstalls the tap and restarts the engine
  in place; `stopEngine` removes the observer
- `AudioCaptureManager.convert` splits buffers into same-format runs
  (`formatRuns`) so a 24 kHz to 48 kHz switch is resampled correctly
- `stopRecording` throws `AudioCaptureError.captureIncomplete` when the
  audio falls short of wall time by more than
  `Constants.captureGapMaximumSeconds`, instead of typing a fragment
- A watchdog ends a recording whose audio stops arriving, and the
  session types what was heard and shows a specific toast
- Add bug record 0032, update `river-pipeline.md`, `tests.md` and the
  changelog

**Why:** with AirPods connected the first mic open switched them to the
call profile and tore the engine down mid-recording. Nothing observed
it, so a 14 s recording captured 1.5 s and typed nothing.
```

Tool calls: `git status/diff --stat/log`, a Read of `docs/conventions/git.md`, `git diff` by path, then `git checkout -b fix/device-switch && git add -A && git commit -F - <<EOF`. 5 turns, 48.2 s, $0.104.

## Observations

- Bare made one commit of fourteen files. The skill made two, split where it saw two fixes: the engine restart, and the handling for a recording that loses its audio.
- The skill typed the watchdog as a `fix`, reading "a recording silently loses audio" as broken behavior rather than a new capability. The branch's own history called it a `feat`. The type seam depends on that call, and here the two readings differ.
- `convert` belongs to the device-change fix, but `AudioCaptureManager.swift` also holds the watchdog, and staging is by path. The file went in the later commit, as the rule then said for a file that serves two commits, so the first commit's restart lands before the conversion it relies on. The skill now asks when one code file holds pieces of two commits. One unrecorded rerun under that rule made a single commit of all fourteen files instead, saying a split by path would land code that needs the other half; that outcome is accepted, since every commit it leaves is complete.
- The changelog and the planning record describe both fixes, and they went in the later commit with that file.
- Both `Why:` bullets carry a measured figure, the 1.7 s stop and the 1.5 s of 14 s, which the subjects cannot.
- Bare read the repo's git conventions and followed them: a `**Why:**` paragraph, a branch, and no trailer. The skill did not read that doc.
- Bare staged with `git add -A`; the skill staged by path.
