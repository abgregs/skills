# 0005 — a probe of the `Why:` judgment and grouping

**Claim.** The skill writes `Why:` when a change has a cause from outside the code and leaves it out when the subject says it all. It groups commits so each stands alone: changes no order can separate, or that exist only for each other, share a commit; independent ones split by type and outcome, each change keeping its tests, with a shared changelog in the later commit; and work of one purpose across several files stays one commit unless reviewing it would take about an hour. Unlike 0001 to 0004, this case measures how often the skill gets these right across repeated runs, so a change to the wording can be compared against a number rather than a single message.

**Input.** Nineteen fixture repos built by [`0005-fixtures.sh`](0005-fixtures.sh), which holds their exact contents. Each is a small Python module with a two-commit conventional history and one dirty change. P1 to P6 were written first and the `Why:` wording was revised against them; H1 to H5 were added afterwards and are held out from that tuning. H6 to H8 were added with the type-seam grouping rule, to test it; H9 to H11 with the rule that binds pieces sharing a file or existing only for each other; and H12 and H13 with the rule that weighs close calls by review time. H12 and H13 are observed, not scored: a close call has no single right answer.

## Observations

- In round 1 every P1 run wrote a `Why:` that restated the mechanism, such as "`range(1, pages)` stopped one short". Naming the mechanism as not a cause stopped it in every later run.
- In round 1 one P6 run left the measured figure in the code comment. The current wording says a comment in the diff does not replace `Why:`, and every later P6 run moved the figure into the message.
- P2 is the unstable fixture: 3, 2, 1, 1, 1, 1, 0, 1, then 3 of 3. Every miss still states the reason, folded into an ordinary bullet ("keys on `user.pk` instead of `id(user)`, which CPython reuses after free"), so these runs miss the label, not the information. The expected answer is itself contested: by P1's standard, `id()` reuse is arguably the mechanism, and the cause from outside the code would be the trigger, a new user served a freed user's profile. The tally checks for the label only, not for which of these it names. Every round-9 `Why:` names the reuse, as in "CPython reuses an `id()` after the object is freed, so a new user got a stale profile". Round 9 is also the only round run with the user's global `CLAUDE.md` hidden, but three runs cannot say whether that, or chance, moved the score.
- Under the earlier grouping line, 7 of 36 runs split a fix or feature from its own tests, reading "same change type" as a reason to put tests in a `test` commit. Under the atomic grouping rule, in rounds 3 and 4, no run split, the rename kept its call sites, the dependency bump kept its adapted call, and every H2 run committed the refactor before the feature.
- Round 4 added the rule that docs go with the change they describe. None of the fixtures carries docs, so this round checks only that nothing else moved, and nothing did. Cases 0001 to 0004 exercise that rule.
- Round 5 grouped by conventional type first, then by "the same fix or a different one". Every H6 run made a `fix` and a `feat` commit, every H7 run made two `fix` commits, every H8 run kept its two scopes in one `fix`, and in H6 and H7 the shared changelog always went in the later commit.
- In round 6, one H2 run folded the extracted helper into the feature that uses it, reasoning that "`report_csv.py` imports `rows` from `report.py`. The `rows` refactor in `report.py` therefore can't be committed apart from the CSV feature." The round-6 rules bound two pieces when either one alone would break, which counts a one-way dependency, while a later pass said the refactor lands first. Round 7 bound only what no order can separate, round 8 asked what calls the new piece, and every H2 run since commits the refactor first.
- Rounds 6 to 9 ran H9, H10, and H11 twelve times each. H9 was always one `feat`, since the refactor shares a file with the feature. H10 was always a `refactor` and a `fix`. H11 was always one `test`, the parameter going with the test that passes it.
- H12, the small close call, was one `test` commit in all nine runs of rounds 7 to 9. H13, at 1,048 lines, was split into three commits, one per suite, in all nine runs, and every H13 run ran `--size` first. One round-7 run explained: "the three files together came to 1048 lines, well over an hour of review, so I split them by target."
- The tally scores commit types and the newest commit's files, not where each test file went. Read by hand for round 5, and listed commit by commit for round 9, every run of H2, H6, and H7 in those rounds, and every round-9 run of H10, put each test file in the commit of the change it covers.
- No run called `git commit` directly or passed `--accept-warnings`. From round 7, when the gate began committing named paths, no run staged a file by hand.
- The skill asks the summary to name the pass behind each commit, such as `bound:` or `weighed:`. Most summaries give the reason in a sentence instead, and some give none for a single-commit fixture, so the tally does not score it.
- The held-out fixtures H1 to H5 scored 15 of 15 on both measures in every round that ran them. Five fixtures run three times each is a small sample; a regression on them is a signal, a perfect score is not proof.
