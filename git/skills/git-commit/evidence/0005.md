# 0005 — a probe of the `Why:` judgment and grouping

**Claim.** The skill writes `Why:` when a change has a cause from outside the code and leaves it out when the subject says it all. It groups commits so each stands alone: changes no order can separate, or that exist only for each other, share a commit; independent ones split by type and outcome, each change keeping its tests, with a shared changelog in the later commit; and work of one purpose across several files stays one commit unless reviewing it would take about an hour. Unlike 0001 to 0004, this case measures how often the skill gets these right across repeated runs, so a change to the wording can be compared against a number rather than a single message.

**Input.** Nineteen fixture repos built by [`0005-fixtures.sh`](0005-fixtures.sh), which holds their exact contents. Each is a small Python module with a two-commit conventional history and one dirty change. P1 to P6 were written first and the `Why:` wording was revised against them; H1 to H5 are held out from that revision. H6 to H13 each test a grouping rule and were written alongside it. H12 and H13 are observed, not scored: a close call has no single right answer.

| Fixture | Change | Expected |
|---|---|---|
| P1 | `range(1, pages)` misses the last page | 1 commit, no `Why:`; the off-by-one is the mechanism |
| P2 | cache key moves from `id(user)` to `user.pk`; a test docstring says CPython reuses ids | 1 commit, `Why:`; contested, see Observations |
| P3 | a `--version` flag | 1 commit, no `Why:` |
| P4 | CSV export gains a UTF-8 BOM; a comment says Excel garbles accents without one | 1 commit, `Why:` |
| P5 | two callers share one email check | 1 commit, no `Why:` |
| P6 | stopwords move to a frozenset; a comment gives a measured 38% | 1 commit, `Why:` |
| H1 | `dist` renamed to `distance` with its two call sites | 1 commit, no `Why:` |
| H2 | a `rows` helper is extracted, then a new CSV renderer uses it (separate new files) | 2 commits, refactor first, no `Why:` |
| H3 | a timeout rises from 5 s to 15 s; a comment gives the API's 9 s p99 | 1 commit, `Why:` |
| H4 | a display name drops the space when there is no last name | 1 commit, no `Why:` |
| H5 | `httpx` bumped with the one call that its new API renames | 1 commit, no `Why:` |
| H6 | CSV export stops dropping its last row; a new TSV export; one changelog lists both | a `fix` and a `feat` commit, changelog in the later one |
| H7 | two unrelated fixes, a duration display and a slug, each with its own test file; one changelog lists both | two `fix` commits, changelog in the later one |

| H12 | tests closing gaps in three suites, 20 lines | observed |
| H13 | tests closing gaps in three suites, 1,048 lines of one-line assertions | observed |

**Method.** As in the README, with two differences: only the skill arm runs, three times per fixture, and the runs go in parallel, each in its own copy with its own `mktemp` message.

## Results

Run on 2026-11-02 against `SKILL.md` and `scripts/` as committed with this evidence, $4.14 for all 57 runs:

| Measure | Correct |
|---|---|
| `Why:` | 39/39: P 18/18, H 21/21 |
| Grouping | 51/51 |

Every fixture scored for `Why:` (all but H6 to H8 and H11 to H13, which test grouping only) got it right in 3 of 3 runs. How these scores moved as the wording changed is in the README's History.

## Observations

- P2's expected answer is contested: by P1's standard, `id()` reuse is arguably the mechanism, and the cause from outside the code would be the trigger, a new user served a freed user's profile. The tally checks for the label only, not for which of these it names. Every `Why:` here names the reuse, as in "CPython reuses an `id()` after the object is freed, so a new user got a stale profile". P2 missed the label in most runs on earlier states of the skill, so three runs cannot rule out chance.
- Every H2 run committed the refactor before the feature that uses it. H9 was one `feat` in every run, since the refactor shares a file with the feature. H10 was a `refactor` and a `fix`. H11 was one `test`, the parameter going with the test that passes it.
- H12, the small close call, was one `test` commit in all three runs. H13, at 1,048 lines, was split into three commits, one per suite, in all three, and every H13 run ran `--size` first.
- The tally scores commit types and the newest commit's files, not where each test file went. Listed commit by commit, every run of H2, H6, H7, and H10 put each test file in the commit of the change it covers.
- No run called `git commit` directly, passed `--accept-warnings`, or staged a file by hand.
- The skill asks the summary to name the pass behind each commit, such as `bound:` or `weighed:`. Most summaries give the reason in a sentence instead, and some give none for a single-commit fixture, so the tally does not score it.
- The held-out fixtures H1 to H5 scored 15 of 15 on both measures. Five fixtures run three times each is a small sample; a regression on them is a signal, a perfect score is not proof.
