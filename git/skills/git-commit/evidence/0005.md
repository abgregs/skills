# 0005 — a probe of the `Why:` judgment and grouping

**Claim.** The skill writes `Why:` when a change has a cause from outside the code and leaves it out when the subject says it all, and it splits commits by conventional type and then by distinct fix or feature, keeping each change's tests with it and putting a shared changelog in the later commit. Unlike 0001 to 0004, this case measures how often the skill gets these right across repeated runs, so a change to the wording can be compared against a number rather than a single message.

**Input.** Fourteen fixture repos built by [`0005-fixtures.sh`](0005-fixtures.sh), which holds their exact contents. Each is a small Python module with a two-commit conventional history and one dirty change. P1 to P6 were written first and the `Why:` wording was revised against them; H1 to H5 were added afterwards and are held out from that tuning. H6 to H8 were added with the type-seam grouping rule, to test it.

| Fixture | Change | Expected |
|---|---|---|
| P1 | `range(1, pages)` misses the last page | 1 commit, no `Why:`; the off-by-one is the mechanism |
| P2 | cache key moves from `id(user)` to `user.pk`; a test docstring says CPython reuses ids | 1 commit, `Why:` |
| P3 | a `--version` flag | 1 commit, no `Why:` |
| P4 | CSV export gains a UTF-8 BOM; a comment says Excel garbles accents without one | 1 commit, `Why:` |
| P5 | two callers share one email check | 1 commit, no `Why:` |
| P6 | stopwords move to a frozenset; a comment gives a measured 38% | 1 commit, `Why:` |
| H1 | `dist` renamed to `distance` with its two call sites | 1 commit, no `Why:` |
| H2 | a `rows` helper is extracted, then a new CSV renderer uses it (separate new files) | 2 commits, refactor first, no `Why:` |
| H3 | a timeout rises from 5 s to 15 s; a comment gives the API's 9 s p99 | 1 commit, `Why:` |
| H4 | a display name drops the space when there is no last name | 1 commit, no `Why:` |
| H5 | `httpx` bumped with the one call that its new API renames | 1 commit, no `Why:` |
| H6 | CSV export stops dropping its last row; a new TSV export; one changelog lists both | a `fix` and a `feat` commit, changelog in the later one |
| H7 | two unrelated fixes, a duration display and a slug, each with its own test file; one changelog lists both | two `fix` commits, changelog in the later one |
| H8 | one fix across two scopes: billing returns cents and the receipt formats them | 1 `fix` commit |

**Method.** As in the README, with two differences: only the skill arm runs, three times per fixture, and the runs go in parallel, each in its own copy with its own `mktemp` message.

## Observations

- In round 1 every P1 run wrote a `Why:` that restated the mechanism, such as "`range(1, pages)` stopped one short". Naming the mechanism as not a cause stopped it in every later run.
- In round 1 one P6 run left the measured figure in the code comment. The current wording says a comment in the diff does not replace `Why:`, and every later P6 run moved the figure into the message.
- P2 is the unstable fixture: 3, 2, 1, 1, then 1 of 3. Every miss still states the cause, folded into an ordinary bullet ("keys on `user.pk` instead of `id(user)`, which CPython reuses after free"). Whether a runtime's behavior counts as a cause from outside the code is the boundary the wording leaves open.
- Under the earlier grouping line, 7 of 36 runs split a fix or feature from its own tests, reading "same change type" as a reason to put tests in a `test` commit. Under the atomic grouping rule, in rounds 3 and 4, no run split, the rename kept its call sites, the dependency bump kept its adapted call, and every H2 run committed the refactor before the feature.
- Round 4 added the rule that docs go with the change they describe. None of the fixtures carries docs, so this round checks only that nothing else moved, and nothing did. Cases 0001 to 0004 exercise that rule.
- Round 5 grouped by conventional type first, then by "the same fix or a different one". Every H6 run made a `fix` and a `feat` commit, every H7 run made two `fix` commits, every H8 run kept its two scopes in one `fix`, and in H6 and H7 the shared changelog always went in the later commit.
- The tally scores commit types and the newest commit's files, not where each test file went. Read by hand, every round-5 run of H2, H6, and H7 put each test file in the commit of the change it covers.
- No run called `git commit` directly or passed `--accept-warnings`.
- The held-out fixtures scored 15 of 15 on both measures in every round that ran them. Five fixtures run three times each is a small sample; a regression on them is a signal, a perfect score is not proof.
